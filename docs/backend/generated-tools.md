# Generated tool host (LF-224 / LF-229)

Implemented in the primary checkout. This document describes offline-verified host behavior; actual Pi/cloud generation and deployment are separate coordinator acceptance work.

## Runtime and capabilities

`createGeneratedToolAdapter()` in `apps/api/src/generated-tool-runtime.ts` validates shared `code-js-v1` specs, runs their 2–5 JSON fixtures, and invokes new JavaScript computation. Tool code runs exclusively in QuickJS 0.32.0 WebAssembly inside a fresh worker. It is never evaluated by Node. Async `run(input, api)` supports `api.readRecords({fields,limit})` and `api.callConnector({toolId,toolVersion,input})` through JSON-only messages.

The shared limits apply: 32 MiB QuickJS heap, 256 KiB stack, **one active worker per API process**, 8 broker calls, 32 KiB source and 64 KiB bounded JSON payloads. The parent starts an **8-second initialization deadline** before creating the worker. Only after the trusted worker has initialized QuickJS, its context and broker does it signal readiness; the parent starts the **4-second guest execution deadline** and permits execution. A separate **12-second total deadline** spans both phases. Absolute deadline checks reject late worker messages even when CPU throttling delays timer delivery. Initialization timeout is `503 TOOL_STARTUP_TIMEOUT`; execution/total timeout is `422 TOOL_LIMIT_EXCEEDED`.

The admission limit is shared across adapter instances and spaces. Contention returns immediate `429 TOOL_BUSY` before constructing another worker; there is no queue, prewarming or time hidden before initialization accounting. Whole registered specs are limited to 128 KiB. Workers are terminated on completion, cancellation or timeout, then capacity is released. These are runtime/worker controls; the QuickJS heap limit is **not a hard process RSS limit**. The guest has no ambient Node APIs, shell, import loader, network transport, environment or server credentials. The trusted worker process itself is ordinary server code.

The broker rechecks the original active auth session, Owner, current definition and exact published binding before each capability access and after connector completion. Record rows are `{id,version,values}`, at most 100 rows, and contain only requested, declared, currently public fields of the current space. Catalog connectors must be explicitly declared, already enabled, exact-version, read-only GET tools. Generated tools cannot call other generated tools or select an arbitrary endpoint. Fixture tests use supplied record/connector JSON only and never contact a connector.

Production uses `apps/api/dist/generated-tool-worker.js`, built as a separate tsup entry. Source development registers the local `tsx/esm/api` loader in a trusted bootstrap. The actual production worker was separately exercised with `execArgv: []`; it does not need tsx.

LF-229 sends those immutable limits from the trusted parent through workerData. The worker imports their TypeScript shape only, avoiding unrelated contract/schema/parser initialization. Its compiled entry shrank from 229.83 KiB to 3.27 KiB with the readiness protocol. Two complete actual-adapter Docker runs at 0.1 CPU / 512 MiB failed under the former 4-second combined initialization/execution deadline; the second failed despite the smaller worker and single slot. Those failed results remain in the [performance evidence](../memory/handoffs/backend/LF-229-88cc9a2e-8c04-4596-9301-c23057a822ef-performance.json). The coordinator explicitly accepted separate initialization/execution limits in catalog21.

DevOps independently rebuilt and ran the complete actual adapter/compiled worker once with the revised phases, at Docker 0.1 CPU / 512 MiB, without network or environment files. All six checks passed: two fixture outputs, different-input invocation, cross-adapter busy response, admitted request completion, fresh request completion and observed phase bounds. Across five admitted workers, startup took 1.297–4.798 seconds, guest execution 0.594–1.106 seconds and the longest result took 5.506 seconds from worker construction. The full two-fixture adapter call took 10.798 seconds including validation/termination overhead; invocation calls took 2.798, 6.606 and 3.190 seconds. Peak observed RSS was 90.7 MiB, not a guaranteed hard process bound. This is Linux arm64 local resource-profile evidence, not actual Render deployment or combined server-traffic acceptance.

## Routes, persistence and authorization

- Owner `GET /api/spaces/:slug/code-tools` returns `{tools: RegisteredGeneratedTool[]}` including source, fixture evidence and SHA-256 source digest.
- Owner `POST /code-tools/proposals {prompt}` uses `AppOptions.toolCodeGenerator`, passes source-free enabled manifests and enabled catalog connectors, and returns a tested candidate or exact registered reuse. It does not register or enable a candidate. Private default literals are removed from model context.
- Owner `POST /code-tools {spec,enable}` checks source/schema/capabilities, runs actual fixtures, then rechecks the original session and registry inside a short transaction. Existing source/schema/capabilities/fixtures are immutable per tool ID/version. Enablement remains an explicit Owner action.
- Owner `POST /code-tools/:toolId/invoke` requires the shared request body: `requestId`, `definitionVersion`, `componentId`, `actionId`, `toolVersion`, `input`. It returns `ToolResult {toolId,toolVersion,result,reused}`. The legacy `/tools/:toolId/invoke` also accepts and validates those binding fields while retaining its old tool-result request compatibility.

All writes reuse existing Google/local AuthApi, Origin and CSRF protection; no second auth implementation exists. Code-tool work binds to the original database session token hash internally, not a public frame token. Local logout aborts outstanding work immediately; final session checks reject late results. HTTP response disconnect aborts a tool even after the request body was received.

Route-wide deadlines are separate from each worker: invocation allows 14 seconds including surrounding authorization/database work; explicit registration allows 65 seconds for at most five fixture workers and surrounding checks. Standalone tool proposals retain their existing 30-second deadline, and whole website generation retains its 90-second deadline. These stricter whole-operation caps can abort a slow multi-tool or five-fixture generation even when each worker individually stays within its limits. They do not silently extend for testing or provider work.

Migration 6 creates `lf_code_tools` and `lf_code_tool_requests`. Calls reserve a durable pending request identity under the space lock before execution. Execution and external connector I/O occur outside business transactions. Commit rechecks Owner/session/binding/registry/capabilities, saves a bounded result, increments invocation count and adds an audit row. Same payload/request ID replays a completed result; another payload conflicts. A concurrent pending duplicate returns `409 TOOL_IN_PROGRESS`, rather than joining the running promise. Interrupted/failed calls are not automatically retried. Startup marks pending reservations failed; use a new deliberate request ID to try again. This recovery model assumes the initial **single API worker process per database** and does not claim distributed exactly-once external I/O.

An invocation rejected with `TOOL_BUSY` has already reserved its request ID, so its durable status becomes `failed` and its invocation count stays unchanged. Repeating that ID returns `409 TOOL_INTERRUPTED` without running code. Once capacity frees, the caller must start a deliberate new request with a new ID. A completed new request replays its saved result and increments the count only once. Fixture testing propagates `TOOL_BUSY` and `TOOL_STARTUP_TIMEOUT` as service failures instead of inventing a failed source fixture or consuming the source repair allowance.

## Website generation and frame integration

`SiteGenerator` receives enabled generated manifests and catalog tools. Proposed `codeToolProposals` are validated and actually tested outside DB transactions. Valid `progress.ui` snapshots are persisted; provider tool progress may claim `writing` only. The host emits `testing`, `ready` or `failed` from real fixture work and stores `job.toolReports`.

Source validation, tool validation/tests and browser preview share one repair. Safe diagnostics include the tool ID and failed fixture name/message, without real record values or result payloads. New source revisions clear old reports. Owner publication revalidates dependencies and atomically saves tested tools with explicit enablement, exact bindings, the definition, retained records, event/history and replay marker. Failed or stale candidates never enable tools or replace the published website.

The trusted frame bootstrap exports `lf.runTool(toolId, toolVersion, input)`. The parent frontend selects the declared endpoint/action from the current component's exact `toolBindings`; preview execution remains disabled. Anonymous/Participant projections remove tool actions and bindings together, keeping the public definition valid and tool source private.
