# LivingForma：从用户场景反推组件与 Pi 工具

更新：2026-10-03。用户明确的两条主线是 **前端的可玩性、变换性** 与 **后端通过 Pi 创建并复用工具**。本文是开发目录与验收设计，下面的组件、工具和案例不是已实现功能。

## 系统怎样创造一个 App

用户描述意图 → Agent 检索组件/工具能力目录 → 判断已有能力与缺口 → 选择组件、绑定数据与动作、组合布局 → 校验并发布 → 持续调整形态，保留数据和链接。

提前建设丰富的前端组件库，而不是提前做许多个固定 App 模板。读书场景中的卡片、评分、进度和筛选，也能组成电影收藏、学习清单或项目看板。Agent 必须根据需求选择组合；不能把“读书”和“习惯”识别成两个硬编码模板开关。

前端组件缺口与后端工具缺口分开处理：缺少可视化组件时，由 Frontend 开发、验证、注册后供 Agent 使用；缺少外部操作时，由 Pi 驱动能力发现和工具提案，再由宿主验证、注册与执行。注册过的工具有版本和执行记录，后续需求可以复用。**Pi 是后端工具创造与执行编排的基础；Google 模型负责理解/规划，不能把产品只做成一个模型聊天接口。**

## 场景分类与组合实例

“变化请求”必须改变结构或行为，不能仅换标题/颜色。前两项为已选正式验收；相机为已确认 Jarvis 里程碑，其他是组件复用与后续扩展候选。

| 类别 / 场景 | 初始组件组合 | 用户继续说什么 | 后端能力或工具缺口 |
| --- | --- | --- | --- |
| 记录收藏：读书 | cover cards + 录入表单 + 状态筛选 + 阅读进度 | 加评分、按评分排序，突出正在读的书 | 可选书目检索/元数据补全工具；真实服务待选 |
| 时间习惯：习惯打卡 | 习惯列表 + check-in 按钮 + calendar-grid + streak | 改为每周目标，展示过去四周完成率 | 主库打卡/日期聚合；不需要外部工具就不制造工具 |
| 专注学习：番茄钟 | 倒计时 + 任务队列 + 进度环 + 会话记录 | 开始时切到专注全屏，结束后显示统计 | 受控本地计时与持久会话动作；提醒服务后续单独授权 |
| 规划组织：旅行计划 | 时间线 + 地点卡 + 分日 tabs + 清单 | 今天下雨，把户外活动移到明天 | 天气/地点只读查询工具；地图 SDK/服务权限另核实 |
| 学习游戏：记忆卡 | flashcard + 翻面按钮 + 进度 + 答题反馈 | 把这组笔记变成测验，只练错题 | 内容处理适配器 + 答题状态；来源与正确性需展示 |
| 创作整理：灵感板 | 可分组卡片 + 标签 + 简单连线/关系视图 | 按主题重新分组，再变成任务看板 | 主库分组/状态转换；任意代码不是前提 |
| 协作决策：投票 | 选项卡 + 投票动作 + 条形结果 + 截止倒计时 | 投票结束后变成结果展示页 | 登录者投票约束、去重和聚合；公开读与写权限分离 |
| 信息观察：个人仪表盘 | 指标卡 + 图表 + 状态徽标 + 更新按钮 | 合并数据源，只展示异常变化 | Pi 创建/复用受控查询工具；采集频率和成本可见 |
| 环境感知：相机讲解 | camera viewport + 开始/停止 + 实时字幕 + 音频状态 | 告诉我现在看到了什么；切回我的书架 | 内置媒体适配器：Gemini 视觉 + ElevenLabs 播报；独立设备会话 |
| 步骤引导：做饭助手 | 步骤卡 + 清单 + 多计时器 + 语音控件 | 切到下一步，显示还没准备的材料 | 受控状态动作，可选食谱查询工具；不凭画面保证食物安全 |

## 前端能力目录：按复用价值分批建设

以下名称是候选，不是已接受 TypeScript 类型。组件的外观变体不算新能力；例如 cover/compact/hero 属于 cards 的变体。先做一组能端到端使用的组合，再从候选池持续扩展，避免提前写几十个没有数据/动作契约的空壳。

| 组件层 | 首批通用基础 | 后续候选 |
| --- | --- | --- |
| 布局与导航 | section/stack/grid、tabs、响应式主画布 | 分栏、可折叠面板、全屏场景、分步导航 |
| 内容与收集 | form、list、cards、empty-state | detail panel、table、tag editor、富文本展示 |
| 数据动作 | 状态选择、rating、check-in、筛选/排序 | toggle、slider、可验证拖放排序、投票选项 |
| 时间与反馈 | counter、progress、calendar-grid、streak | timer、timeline、倒计时、多时区提示 |
| 可视化与组织 | 与读书/习惯数据绑定的摘要 | bar/line chart、kanban、关系视图、地图视图 |
| 趣味交互 | 与真实动作关联的局部反馈、连续布局变形 | flashcard、quiz、转盘/随机选择、拖放匹配 |
| 媒体与设备 | Jarvis 里程碑：camera viewport、voice input、caption、audio output | 文件预览、画板、受限 3D 场景 |

Owner orb 是产品外壳，不由 Planner 生成或隐藏鉴权；访客只看到组装出来的网站。Toast、dialog、焦点管理等基础原件由 Frontend 维护，不必全部暴露给模型自由组合。Motion、精选皮肤与变形规则服务所有组件，不做成每个模板一份动画。

## Agent 如何知道该用哪个组件

每个可发现组件需要一份受版本管理的 manifest，至少说明：

- `id/version` 与能力描述、适用场景、示例；标签用于检索，不能硬绑定单一 App 类型。
- props schema、数据字段绑定、输入/输出类型、允许的动作/事件。
- 可组合父子关系、布局约束、变体与受控 token；未知属性拒绝。
- 所需能力/权限、外部工具引用与版本、加载/空/错误状态。
- 手机和桌面行为、键盘/屏幕阅读器支持、reduced-motion 降级。
- 稳定身份与迁移约定、自动化/人工验收证据、可用状态。

建议让 Planner 先按意图检索能力摘要，再读取入选 manifest，生成 AppSpec 与能力绑定。不要每次把整个组件库源码塞进 prompt。校验器检查组件引用、字段类型、动作权限、工具可用性与组合约束；未知能力生成明确缺口，不渲染假按钮。

## Pi 工具创造的验收重点

第一条纵向链路应展示：用户提出一个现有工具库不能满足的只读查询 → Pi 驱动生成受限 ToolSpec → 宿主验证目标/参数/返回 schema/额度 → 测试 → Owner 启用并注册版本 → 组件绑定返回数据 → 第二次请求复用同一工具，而非再次临时生成。

首版只读 GET 是可验证起点，不是产品能力永久上限。之后可扩展组合工具、转换器、受控写入连接器；外发、破坏性操作或收费仍按用户约定确认。新增可执行实现需经过隔离、测试、审查与注册，不能用“Pi 能写文件/运行 shell”代替产品运行时的执行边界。相机/语音属于开发者提供的内置媒体能力，不能冒充 Pi 刚刚发明的工具。

未实现的场景可以提出方案和缺口，不能演示成可运行。组件装配正确、工具真实创建、结果进入 UI、再次复用，四项都要有证据。

### 本地 Pi 源码核查（非调用测试）

本轮只读检查了用户的 `project/pi` checkout（commit `83692682f095528f8b71652ddacff7075e36e893`）：`packages/agent/src/types.ts` 定义 schema + execute 工具，`packages/agent/src/agent-loop.ts` 在调用前校验参数；`packages/coding-agent/src/core/extensions/loader.ts` 的 `pi.registerTool()` 会刷新工具目录，`examples/extensions/dynamic-tools.ts` 有启动后动态注册示例。Pi 已提供动态注册机制，不能描述成完全不支持动态工具。

Web 产品可选 agent-core 的嵌入路径，或 coding-agent SDK/extension 的注册路径；LF-100 必须选定一条并验证接口，不能混用。当前 core 通过 `agent.state.tools` 管理工具，run 开始会取工具快照；同一 run 新工具可见性需验证 `prepareRequest` / `prepareNextTurnWithContext` 更新 `context.tools` 的方式，不能臆造 `agent.setTools()`。Coding-agent 的注册与 `setActiveTools()` 启用也不同。具体包名/版本在实现时按锁定 checkout 核实。

上述机制不自动提供 LivingForma 的 ToolSpec 生成、空间权限、数据库版本、凭据引用、去重和重启恢复。后端持久化有效规格，再以受控执行器重新构造 handler 并注册；Pi 的对话 session 不是业务工具库。

## 角色分工与验收顺序

- Coordinator：维护场景矩阵和共享 manifest/数据/动作契约，确定每批高复用组件与工具范围。
- Frontend：预制可信组件、实验场和组合实例，验证两种结构明显不同的 App，以及同数据跨形态切换；持续提出组件缺口。
- Agent：Pi 运行时、组件/工具检索与装配规划、缺口分类、ToolSpec 创建和复用、Gemini/ElevenLabs 适配。
- Backend：注册表存储、校验/授权/执行边界、数据绑定、持久化与 SSE。Pi 不直接绕过这些边界改数据库。
- DevOps：Google OAuth、HTTPS/域名、运行环境与免费额度；QA：独立验证组合泛化、工具复用、数据保留与跨浏览器一致性。

LF-100 定契约；LF-110 建首批组件库及组合演示，LF-120/130 接真实数据与 Pi 工具闭环；LF-150 验证同一运行时的组合、变形和复用。LF-180/181/182 → LF-185 接语音/相机；之后 QA 与上线。候选池不是要求第一版一次性交付全部组件。
