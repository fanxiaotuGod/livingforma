# Generated backend tools and live UI formation

Accepted implementation contract · 2026-10-03 America/Vancouver. User's active objective requires AI-created frontend pages, newly generated backend tools, and UI components visibly changing while generation runs. Existing fixed HTTP recipes remain available; they are not the limit of new backend logic. This document specifies implementation, not completion.

## Tool creation and reuse

`GeneratedToolSpec` in packages/contracts/src/generated-tools.ts carries original JavaScript source, declared bounded JSON input/output schemas, at least two JSON-only fixture tests, and explicit read-only capabilities. Entry point is `function run(input, api)` (async supported). Pi can create arbitrary new computation/transformation/aggregation logic within these capabilities. It does not obtain host shell, package installation, credentials, arbitrary database or network access. New external account permissions remain truthful capability gaps until implemented and authorized.

Use quickjs-emscripten0.32.0 in a separate host-owned Worker and fresh QuickJS runtime/context per execution. Root installed the exact dependency in API. Set shared heap/stack/deadline/broker/data limits and a global concurrency of one; extra requests receive TOOL_BUSY. Use explicit bounded startup (8 seconds), guest execution (4 seconds) and total Worker lifetime (12 seconds), with no work hidden before the timers. The smaller compiled Worker receives trusted limits from the parent and does not initialize the host parser/schema modules. The invocation route allows 14 seconds and registry fixture batches 65 seconds. Website generation retains its overall 90-second cap and standalone tool proposals their 30-second cap; these stricter job limits can truthfully stop long work before every individual phase allowance is used. These phase limits address measured free-tier coldstart variance and require actual Docker acceptance before release. parent handles cancellation and terminates timed-out workers. QuickJS heap limits are not a claim of a hard total process RSS limit. The trusted Worker imports the mature runtime, then treats model code as guest data. No model source is imported/evaluated as Node code. Ordinary limit/functionality tests only; further advanced bypass research is paused after the platform notice.

Worker source filename apps/api/src/generated-tool-worker.ts is built as an additional tsup entry via API build script (Root owns manifest); use compiled dist/generated-tool-worker.js in production and appropriate Node24/tsx source handling locally. Backend owns both runtime and worker source. Build must retain QuickJS WASM/dependencies in the existing Docker runtime.

Guest `api.readRecords({fields,limit?})` obtains only declared public fields from the current authorized space, within JSON/record limits; it cannot select another space or private field. Guest `api.callConnector({toolId,toolVersion,input})` calls only declared, already-enabled exact versions of existing host read-only connectors. No arbitrary URL/fetcher and no new provider spending. Broker responses are bounded JSON; session/cancellation is checked before and after I/O. Tests use declared JSON fixtures instead of real connector calls. Source/schema/capabilities are immutable per version.

Host performs shared shape/syntax validation and fixture tests before registry admission. Preserve actual test results and source digest; persist versioned code tools separately from legacy HTTP tools, with common metadata discovery. Website generation includes optional Proposal.codeToolProposals and receives existing enabled GeneratedToolManifest metadata (no private records/defaults or provider secrets). Prefer reuse when compatible; incompatible source requires an explicit new version. A model cannot silently overwrite an existing version. Publish tested tool candidates plus the generated definition atomically; the Owner's explicit publication approves their read-only capabilities. Incomplete/failed tool candidates never replace the live site or gain enabled registry status.

Generation testing/external broker work stays outside long database transactions. Recheck current original session, source revision, schema/base version and required connector enablement at publication. Persist toolReports in Owner-scoped GenerationJob. At most one host repair is shared by source, tool and actual preview failures; no independent hidden retry loops.

Standalone Owner workflow may use POST /api/spaces/:slug/code-tools/proposals `{prompt}` to invoke GeneratedToolGenerator and test/return a candidate or enabled exact-version reuse; POST /code-tools `{spec,enable}` explicitly validates/tests/registers; GET /code-tools returns Owner manifests/source/test evidence. All mutations require current session, Origin and CSRF; revalidate after model/test work. These endpoints do not expose tools to a browser frame for arbitrary registration.

## Bound invocation

ComponentSpec.toolBindings is additive and only valid on generated-site: `{actionId,toolId,toolVersion,kind:'generated'|'catalog'}`. Every binding requires the same component's tool.invoke action; IDs and exact target versions are unique. Existing tool-result.toolRef remains backward compatible.

The child API is `lf.runTool(toolId,toolVersion,input)`. Parent selects a matching binding from the current component/definition, validates bounded JSON and current identity/page/frame revision, then uses protectedRequest to invoke the matching generated or legacy host endpoint. The frame cannot choose arbitrary endpoints or registry/admin actions. Frame state contains only public binding metadata, not source/tests/endpoints/credentials. Preview tool invocations are disabled; preview clearly reports this rather than attempting production effects. Anonymous invocation requests host login without auto-replay; current tools remain Owner-only until a separately accepted participant/public policy exists.

Generated invoke POST /api/spaces/:slug/code-tools/:toolId/invoke uses generatedToolInvocationSchema: requestId, definitionVersion, componentId, actionId, toolVersion, input. Validate exact current binding/permission/enabled version before execution and again before committing result. Legacy endpoint can accept equivalent optional binding fields while retaining existing explicit tool-result behavior. Reserve durable request identity before execution, run outside transactions, revalidate then save bounded result/audit/count. A completed same request replays; payload conflicts fail; a pending duplicate returns TOOL_IN_PROGRESS and does not run again. An interrupted pending run is reported honestly and never automatically repeats I/O. The generated-tool endpoint does not coalesce pending promises or promise arbitrary multi-replica external exactly-once.

## Visible evolving UI

GenerationEvent.ui and SiteGenerationProgress.ui use generationOutlineSchema: version1, optional title/skin, flow/split/grid layout, up to24 stable sections with bounded kind/label/columns/items. This is intermediate visual vocabulary, not a limit on the final generated website. No HTML/CSS/JS, record values or arbitrary styles enter this outline. Emit only actual Pi/tool argument checkpoints; the SDK may deliver a complete argument snapshot instead of token-by-token text, so do not fabricate progressive source or smooth percentages.

Host validates/sanitizes and durably saves each accepted outline, scoped by job/sourceRevision/sequence. Frontend displays a separate safe wireframe with Motion layout/size/entry transitions; reduced-motion uses immediate updates. Stable IDs preserve continuity. Missing model outline means honest waiting, not timer-created components. Partial source remains escaped text. Validated complete source replaces the staged wireframe with existing isolated preview; failed revisions leave the published application available.

GenerationEvent.tool identifies actual tool-writing/testing/ready/failed activity. Agent emits writing from real source checkpoints; host emits testing/ready from actual execution results. Owner sees generated tool source and test results alongside HTML/CSS/JS when present. All product UI is English.
