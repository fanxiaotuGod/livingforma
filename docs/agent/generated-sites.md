# General Pi website generation

LF-221 implements `generateSite: SiteGenerator`, exported by `@livingforma/agent`. The same Pi/Gemini source-authoring tool handles ordinary website requests. There are no intent keywords selecting whole-page templates. Its single `submit_site` result contains a model-authored outline, HTML/CSS/JavaScript, entity schema, actions, summary and honest capability gaps. A generic envelope pairs that artifact with one `generated-site` surface. The separate 60-module composition planner excludes this surface and directs existing generated sites back to the studio.

This implementation was verified offline with the real Pi agent loop and a clearly mocked provider event stream. It is not evidence of a new real Gemini generation, a deployed generator, or an end-to-end generated-page browser acceptance. LF-220/222 supply the host/studio; coordinator wires the export and reserves real-provider acceptance. No environment file was read, provider called, allowance reset, dependency installed, generated code host-executed or deployment performed in LF-221.

## Source and progress

The source prompt describes the actual bridge and sandbox: `await lf.ready` and every record mutation resolve to a complete projected state, values live in `record.values`, `lf.subscribe` updates that state, preview writes are disabled, and `lf.reportReady()` follows the first render. Images use explicit `lf.pickImage()` / `lf.image()` and asset IDs. HTML contains body markup, CSS and JavaScript occupy separate fields, listeners use `addEventListener`, and startup uses an async IIFE. The prompt requires responsive layout, keyboard access, reduced motion, empty/error states and truthful unavailable-service feedback. It does not invent external images, uploads, AI/media services or paid capabilities. New generated backend tools are the separate LF-225 extension.

Actual Pi `message_update` events are inspected only for `submit_site` `toolcall_start`, `toolcall_delta` and `toolcall_end`. Only explicitly present `artifact.html/css/js` strings and a shared-schema-valid `outline` may become a checkpoint. The outline is the first tool-schema field and maps to `SiteGenerationProgress.ui`, allowing the trusted studio wireframe to follow real model structure. Invalid/duplicate outline IDs, markup labels and credential-shaped values are withheld. Plain assistant text, thinking, raw deltas, arbitrary arguments and other tools never enter progress.

Progress is deduplicated, limited to 50 callbacks and 160,000 source characters per attempt, and stops after cancellation. There are no timed fake code chunks or percentages. The installed Pi 1.0.1 Google adapter currently emits function-call argument snapshots; it does **not** guarantee character-by-character source streaming. If a provider delivers the complete function arguments at once, the app gets that real checkpoint, not fabricated earlier milestones. Stage messages report start, received source and performed validation only.

The current definition is strictly parsed and cloned. Record values and session metadata are not accepted as extra input. Private `defaultValue` fields are removed again inside the generator, including repair fields matching private IDs in the current definition. The host independently strips these inputs and restores authoritative private metadata before publication. Source evolution preserves the prior generated surface ID; proposed schema changes still pass shared evolution and retained-record checks in the host. This generator cannot change records, the URL or the already-published definition.

## One request, one host repair

Each `generateSite` invocation configures Pi for **one provider request**, at most 6,000 output tokens, a 60-second timeout and the shared one-run concurrency bound. Google automatic retries remain zero. Gemini model selection and the verified-free gate are unchanged. The generator requires an injected durable `ProviderBudgetStore` even in development; it cannot fall back to the old local JSON ledger. Each reservation occurs before the call and remains consumed after cancellation/failure.

A complete well-shaped candidate is parsed as a shared `Proposal`, then checked with `validateGeneratedArtifact` and `validateEvolution` without executing JavaScript. A semantically invalid candidate is returned for the host's authoritative rejection, with a truthful validation checkpoint. This is deliberate: LF-220 owns **one repair shared by static checks and browser errors**. Throwing away the candidate before the host receives it would make static repair impossible; silently repairing inside Pi would spend an untracked second allowance. The generator never retries internally or calls an invalid candidate approved/previewed/published. Malformed or missing tool output fails without inventing a replacement candidate.

On the one host-authorized repair, the generator receives the actual candidate and up to eight bounded concrete diagnostics. Credential-shaped diagnostics are withheld. The repair uses the same single-request budget; the host owns the durable repair count and disallows another. Progress input cannot grant publication authority.
